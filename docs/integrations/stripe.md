# Stripe test-mode boundary

DeBait has a narrow server-side adapter for retrieving and canceling one exact PaymentIntent. The running application does not enable it yet, but a standalone real Stripe test-mode smoke run has verified the adapter against a user-controlled sandbox account.

The adapter accepts only an `sk_test_` key and keeps network access disabled unless the caller explicitly enables it. It verifies the configured account through `GET /v1/account`, retrieves the exact PaymentIntent, rejects live-mode or mismatched objects, and rechecks eligibility immediately before `POST /v1/payment_intents/:id/cancel`. It sends `cancellation_reason=fraudulent` and the persisted DeBait action ID as Stripe's idempotency key. A later retrieval supplies independent read-back state and `amount_received` evidence.

The supported statuses follow Stripe's [PaymentIntent cancellation reference](https://docs.stripe.com/api/payment_intents/cancel). Retrieval follows Stripe's [PaymentIntent retrieval reference](https://docs.stripe.com/api/payment_intents/retrieve). The API version is required configuration rather than a hidden default; Stripe's [versioning reference](https://docs.stripe.com/api/versioning) must be checked again against the test account before a live smoke run.

Local transport tests pin `2026-08-26.dahlia` to prove request construction and fail-closed validation. The real sandbox smoke used the account's compatible `2024-09-30.acacia` version; the API version is always explicit configuration rather than a hidden default.

The defender adapter exposes no create, confirm, capture, refund, transfer, payout, recipient or arbitrary request method. A separate driver-only client creates exactly two equal-amount test PaymentIntents with distinct `scam-linked` and `control` provenance metadata. It uses a test key, verifies the configured account and validates that both returned objects are distinct, non-live and `requires_confirmation`. The driver does not confirm either object. Neither an amount nor model output can select the protected object.

The pair creator and defender adapter were also exercised against a real Stripe **test** sandbox on September 13, 2026. The driver created two distinct equal-value $250 PaymentIntents in `requires_confirmation`; the adapter canceled and read back only the scam-linked object while the control remained `requires_confirmation`. Repeating the logical operation refused the already-canceled state rather than creating a second effect. This proves a narrow adapter checkpoint with test objects and no real funds. Wiring the self-directed agent loop to all four live provider adapters remains a separate end-to-end task.

The `/callbacks/stripe` endpoint preserves the exact bounded request body for signature verification, accepts any valid `v1` signature within a five-minute timestamp tolerance, rejects live-mode and unsupported events, resolves the PaymentIntent through the trusted resource registry and only then persists a sanitized event. Local transport tests cover valid signatures, body tampering, stale signatures, unrepresentable timestamps and unbound objects. A real Stripe webhook delivery remains a separate live check.
